## 一、业务架构评审

### 1.1 做对了的

| 设计 | 评价 |
|---|---|
| 五段管线 C1采集→C2归一化→C3筛选→C4富集→C6组装→C7渲染→C8语音→C9发布 + C5记忆 | 与真实业务流程（抓新闻→判时间→过滤→AI改写→排版→出刊）一一对应，阶段职责边界切分准确 |
| 红线#1 唯一裁决点（normalize） | 「无 publishedAt 一律丢弃」收敛到单一函数 + 类型级保证，杜绝 gzinfo 时代兜底散落 9 处的问题 |
| 红线#2 确定性归属（assignSection） | 板块归属由内容关键词打分决定，架构方向正确 |
| 红线#3 漏斗（funnel.ts 逐字移植） | L0 硬排除→地域→维度→商机/风险追踪器的行为口径与 gzinfo 保持一致 |
| 记忆单一写者（memory） | 全仓库只有一处写 history，避免多写者静默失效 |

### 1.2 业务架构缺陷（按严重度）

- **B1【P0】红线#3 实际被架空。** funnel 注释声称「真正的相关性准度交给 AI 回检」，但 enrich 里**没有**任何 AI 相关性回检——所有 finance/gz 条目无维度命中也全部放行，再由 assignSection 兜底塞进 policy_market。gzinfo「中原再担保/黄金周出游误入面板」的教训在 2.0 没有对应防线。
- **B2【P0】报告级 LLM 调用没有喂真实内容。** enrich 的第二个 LLM 调用 prompt 只给了各板块**条数**，hero_line/insights/must_read 全靠模型编造；`must_read.url` 无条目可对应，生产环境必然产生幻觉死链。
- **B3【P1】历史库只写不读。** C5 每日写入 history，但管线没有任何「回放去重」——同一 URL 明天还会再上榜，跨天重复卡片无法避免。
- **B4【P1】`rollingSince` 实际是坏的。** 历史条目 `date` 存的是 "MM/DD" 展示格式，`Date.parse("09/11")` 返回 NaN，30 天窗口永远返回空；且所谓滚动只是 5000 条截断，从未按日期裁剪。
- **B5【P2】红线#2 存在灰色地带。** `assignSection` 读 `category==="ipo"/"gd-ipo"` 直接归 IPO、`category==="tech"` 增补关键词。可辩护（isIpo 是内容态、参考区豁免是展示窗口判断），但与文件头「绝不读 category」的表述冲突，边界应显式写明：**category 仅可作为 IPO 内容态来源，不得参与一般板块归属**。
- **B6【P2】时间精度回退。** ReportItem.date 只到 "MM/DD"，用户要求卡片显示精准发布时间（gzinfo 股票卡片规范）；且股票市场卡（C10）整体未建。

## 二、技术架构评审

### 2.1 做对了的

- **分层与依赖方向**：contracts（零逻辑）→ services（只依赖端口）→ adapters（唯一副作用）→ orchestrator（唯一装配点），架构门禁机器可查且通过。
- **端口设计**：FileStore/Clock/LlmPort/HttpClient/Logger 五端口覆盖全部副作用面；e2e 测试用 MemFs/FakeHttp/FakeLlm 离线跑通全管线，注入架构的价值已被测试证明。
- **技术选型**：rss-parser/cheerio/jsonrepair/tsx 与业务成熟度匹配，无过度工程；CI 门禁顺序（arch→type→test→daily→pages）正确。

### 2.2 技术架构缺陷

- **T1【P1·已修】C1→C2 契约类型不诚实。** IngestResult 声称 `ArticleInput[]`（publishedAt 必填）但 C1 实际产出 `RawArticle[]`——「类型阶」此前只在文档自洽。已改为诚实契约并删除无人使用的 `rawArticles` 字段。
- **T2【P1】Clock 端口存在但没人用。** `withinWindow` 直接 `Date.now()`，且 `ctx ? Date.now() : Date.now()` 是死代码；窗口过滤无法注入时间、不可测。
- **T3【P1】服务层直读 `process.env`。** assemble 的 MAX_PER_SECTION、select 的 FETCH_WINDOW_DAYS 在模块加载期固化读取——环境是隐式副作用，违背自家端口原则，应经 ctx/config 注入。
- **T4【P1】LLM 调用模式：逐条 + 串行。** enrich 每条一调、`await` 串行——数百条即数百次调用；gzinfo 全管线约 6 次。CI 每 15 分钟跑一次的成本不可行，必须批量化 + 并发池。
- **T5【P1】AI 失败零观测。** per-item catch 吞错（不进 ctx.errors、不打日志），LLM 无 quota 统计——「全 AI 失败的空壳报告」与正常报告无法区分。
- **T6【P2】CI 后端假设错误。** daily.yml 默认 `LLM_BACKEND=claude-cli`，但 Actions 环境没有已登录的 claude CLI，必然静默降级为无 AI 稿。应显式设 openai/deepseek + secrets，或 `SKIP_AI=1` 明示。
- **T7【P2】采集层两处粗糙。** `fetchCrawlers` catch 算出 msg 却丢弃；`fetchScrape` 通用 `<a>`+`<time>` 抓取过朴素——多数列表页无 `<time datetime>`，publishedAt 缺失即被红线#1 丢弃，实际产出≈0，需要 per-site 选择器（gzinfo crawlers 目录尚未迁移）。
- **T8【P2】CrawlerRegistry 未接入主链路。** runPipeline 未装配 crawlers，IPO 六源 + 广州商机三源目前不在 2.0 管线内。

## 三、实现优美度评审

### 3.1 做对了的

- 命名统一（阶段号 C1-C9 + 目录名即服务名），每个文件头有职责 JSDoc；
- render/voice/assemble 为纯函数，esc() 全量 HTML 转义，注入无死角；
- 模式运用恰当（Ports&Adapters、单一写者、类型阶）而非堆砌；funnel 逐字移植保证了行为等价；
- 组合根 69 行完成装配，可读性好。

### 3.2 实现缺陷

- **Q1【P1】三处重复定义。** 板块中文标签在 assemble.sectionLabel / voice.SECTION_LABEL / render.SECTION_META 定义了 3 遍；assemble.TIER_WEIGHT 与 contracts 已有的 SOURCE_TIER_ORDER 重复。应收敛到契约层单一常量。
- **Q2【P2】assignSection 词表硬编码在函数体内**，应提为数据（常量或并入 sources.keywords.json），运营调词不必动代码。
- **Q3【P2】RunMode.skip-ai 的 summaryCache/relevantUrls 是死字段**——enrich 从不读取。按「冗余即删」原则应裁剪为 `{kind:"ai"} | {kind:"skip-ai"}`。
- **Q4【P2】测试面缺口**：select（窗口/评分）、assemble（排序/单源配额）、memory（合并/滚动）、render（golden snapshot）、voice 均无测试；normalize 测试原用 `as unknown as` 强转（已改为注入 SilentLog）。
- **Q5【P2】轻微职责重叠**：excerpt 兜底 / isIpo 推导 / tier 补齐在 fetchAllSources 与 normalizeOne 各做一遍，可收敛到 C2 一处。
